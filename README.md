# Ripple

A short, calm attention-training game, built as an anti-doomscrolling
product rather than another app competing for endless screen time.

Live: [ripple-omega-eight.vercel.app](https://ripple-omega-eight.vercel.app)

## What it is

Shapes ("pulses") drift in from the edges of the screen toward the center
at a steady rhythm. One shape, shown at the start of the round, is the
target. Tap only the target and let everything else pass by. This is a
Go/No-Go task, a real, established paradigm for measuring sustained
attention and response inhibition, not an invented game mechanic.

Rounds are short (75 seconds) and end on their own. There is no endless
mode, no leaderboard, and no push notification nagging you to come back.
The daily streak only counts a player's first three rounds; playing more
is still allowed, it just does not add streak value, on purpose, so the
product does not reward using it as a time sink.

## Features

- Canvas-based game loop with a difficulty curve that ramps in-round
  (spawn rate, shape/color similarity, and two mid-round target switches
  that add working-memory load)
- Email sign-in (Cognito), fully optional; the game works completely
  without an account
- Server-validated daily streak, so it cannot be spoofed from the client
- A focus score derived from actual behavior (reaction time, false-tap
  rate, miss rate), not a cosmetic counter
- An in-app stats page charting focus score over time for signed-in
  players
- Adaptive difficulty: two small machine learning models, trained
  offline and running client-side or in a serverless function, predict a
  learned focus score and personalize where each returning player's next
  round starts on the difficulty ramp
- Consent-gated webcam attention tracking (MediaPipe Face Landmarker,
  entirely on-device) that pauses the round when you look away and
  resumes without costing round time
- Installable PWA (works offline for the core game)

## Architecture

```
Browser (Next.js PWA)
  |
  |-- Canvas game loop (client-only, no server round-trip during play)
  |-- Cognito sign-in/sign-up (direct client SDK calls, no server involved)
  |-- MediaPipe face detection (fully on-device, no video ever leaves the browser)
  |
  |-- POST /api/session  (signed-in only)
  |     -> verifies the Cognito ID token
  |     -> applies the streak-cap rule server-side
  |     -> runs the difficulty model, persists next-round ramp start
  |     -> writes a summarized record to DynamoDB
  |
  |-- POST /api/telemetry  (works signed-in or anonymous)
  |     -> uploads raw per-round telemetry to S3 for future retraining
  |
  \-- GET /api/sessions  (signed-in only)
        -> returns a player's own session history + streak, for /stats
```

Streak logic is server-validated on every request; the client never
computes or reports a streak value itself, so it cannot be spoofed. The
webcam feature never sends video or frames anywhere: detection runs
entirely in the browser via WASM.

## Machine learning

Two small `RandomForestRegressor` models (scikit-learn), each transpiled
to plain JavaScript with `m2cgen` so they run directly in the browser or a
Vercel serverless function, with no separate inference server.

**Why RandomForest instead of the originally planned gradient-boosted
trees:** `m2cgen` does not support scikit-learn's `GradientBoostingRegressor`
at all, only `RandomForestRegressor` or actual XGBoost/LightGBM models.
RandomForest was chosen to stay within pure scikit-learn with no new
dependency; for a feature set this small, the difference in accuracy
between the two algorithms is not meaningful.

**Training data** is entirely synthetic, generated by simulating around
400 virtual players with varying skill and consistency playing through
the game's real difficulty curve (see `ml/simulate.py`). Reaction-time and
error-rate ranges are loosely grounded in published Go/No-Go task
findings, adjusted for this game's slower, more deliberate pacing. This
was a deliberate choice over requiring real human play data up front, and
the raw telemetry pipeline (`/api/telemetry` to S3) exists specifically so
the models can be retrained on real player data as it accumulates.

**Model A, focus score:** predicts the same score the honest, interpretable
formula in `src/lib/game/scoring.ts` already computes from behavioral
features. It starts as a learned approximation of that formula. This
sounds circular, and at the moment it is: the value is that the model can
later be retrained on real telemetry and diverge from the formula to
better reflect actual player behavior, without changing anything in the
game's UI or API.

**Model B, difficulty personalization:** predicts where a returning
player's next round should start on the difficulty ramp (a single value
from 0 to 1), from this round's performance and their previous starting
point. A new or signed-out player always starts at 0, reproducing the
original fixed curve exactly. The label used to train this model is a
simple rule (raise the starting point after a strong round, lower it
after a weak one, drift only slightly otherwise), which is itself a
placeholder the model can outgrow once real outcome data exists.

Both models were kept deliberately small (20 trees, depth 5): a first
attempt at more trees and more depth produced a 144,000-line JavaScript
file per model, which is not something to ship in a web app bundle.

## Project structure

```
src/
  app/                Next.js routes (game, account, stats, API routes)
  components/         React components (game UI, welcome screen, consent, toggles)
  lib/
    game/              Canvas engine, difficulty curve, scoring, rendering
    auth/              Cognito client wrapper, auth context, JWT verification
    attention/          MediaPipe wrapper, camera consent/tracking hook
    ml/                Generated model JS + typed wrappers
    theme.ts            Shared color palette (DOM and Canvas)
    streak.ts            Pure streak-cap logic
    dynamo.ts / s3.ts     Server-only AWS clients
infra/                  AWS CDK stack (Cognito, DynamoDB, S3, IAM)
ml/                     Python: synthetic data generation and model training
```

## Local development

```bash
npm install
cp .env.example .env.local   # fill in values, see infra/README.md
npm run dev
```

The service worker is disabled in development, so `npm run dev` behaves
like a normal Next.js app.

To retrain the ML models:

```bash
cd ml
python -m venv .venv
.venv/Scripts/activate        # or source .venv/bin/activate on macOS/Linux
pip install scikit-learn pandas numpy m2cgen
python simulate.py            # writes ml/data/synthetic_sessions.csv
python train.py               # writes src/lib/ml/*.js
```

## Deploying

Infrastructure first (see `infra/README.md`), then the app:

```bash
npx vercel deploy --prod
```

Vercel needs the same environment variables as `.env.local`, set in the
project's dashboard (Settings, Environment Variables).

## Known limitations

- The ML models are trained entirely on synthetic data; they have not yet
  been retrained on real player telemetry.
- Attention tracking uses face presence only, not gaze or head-pose
  estimation, a deliberate scope choice for robustness over precision.
- A signed-in player's personalized difficulty starting point is not
  fetched on page load, only updated after each round in the current
  session, so it resets to the default on a fresh page load until a round
  completes.
- No automated test suite yet; correctness has been verified through
  manual end-to-end testing (including via curl and AWS CLI against a
  local dev server) rather than a CI pipeline.
